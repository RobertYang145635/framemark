## 3. 这一轮（rc50 → rc57）做了什么

1. **「经典单行」只改预览的根因**：Android 的 `assets/x1ir.zip` 解包身份原来只看
   `manifest.json` 的 `schema + generatedAt + 样式数`。数据侧改 designs/variants/text-slots
   时这三项不变，升级安装（`install -r` 保留数据）就继续用旧解包。现在身份 =
   manifest 三项 + **随包 zip 的 CRC32 与未压缩大小**（读 APK 中央目录，不解压）
   + **构建标签**，并写 `files/x1ir/.fm-bundle-identity` 标记；老解包没有标记，
   必然不匹配，升级后重解一次。
2. **Ultra HDR 封装 OOM**：`UltraHdrAssembler` 原来把整张 JPEG 逐字节塞进
   `ArrayList<Byte>`（36.9 MB 主图 ≈ 700 MB）。改成一次段扫描 + 按段复制；
   顺带修了替换 ICC 时 `tiffStart` 用源坐标导致 MPF 偏移错的 bug。
3. **大尺寸 HEIC/WebP 导入**：先 `inJustDecodeBounds` 读尺寸，按
   `memoryClass × 55% ÷ (4 字节 × 2 张)` 算像素预算，超出按 2 的幂降采样，
   记 `HEIF_IMPORT_DOWNSCALE`；不再稳定地同时持两张全尺寸位图。
4. **选择器兜底**：`pickPhoto/pickDocuments/pickWatermark/pickPresetDocument/createPresetDocument`
   统一走 `launchPicker`，捕 `ActivityNotFoundException`/`SecurityException` 并提示改走相册。
   （日志标签不能以 `FM_` 开头，架构闸门会拦，见第 5 节。）
5. **预览统一**：187 张全部用山景样片重出。原图不在仓库（x1ir.zip 的 15 个历史版本里
   `photo.png` 一直是荷花，git 里也没有被删的山景图），样片是从现存最大的山景渲染
   （1440×1080）裁掉烧进去的页脚、放大到 2667×2000，并写入随包 `exif.jpg` 的 EXIF。
   重出脚本：`scripts/qa/rerender-previews.py`。
6. **双端一致性实测**（同一张 12288×17748 的 200 MP 照片 + 经典单行）：
   手机导出 12288×19112，桌面引擎 `source_canvas` 同为 12288×19112；
   桌面预览与手机成片缩放后平均像素差 2.03/255，页脚文字/字标/位置一致。

## 4. 必须知道的机制

### 4.1 引擎与数据

- Android 与桌面跑的是**同一份 Rust 排版代码**，数据也都是同一份 `x1ir` 包，
  所以双端像素级一致是默认状态；不一致时先查数据/参数，再查平台差异。
- Android 从 `assets/x1ir.zip` 解包到 `files/x1ir/`；桌面把同一个 zip 解到
  `delivery/FrameMark/data`（打包时）。**改数据要同时照顾两侧**：桌面靠重新打包，
  Android 靠 4.1 的身份机制触发重解。
- 应用读 `composeResources/files/data/{capabilities,inspector-meta,previews,taxonomy}.json`，
  引擎侧真源在 `engine/data/`；**两份必须同步**（有测试盯计数）。

### 4.2 预览

- 187 张 `previews/<cardId>.webp`，480 长边、WebP q92；`previews.json` 也存两份。
- 样片必须带 EXIF，否则手写卡的品牌/机型/参数行是空的。
- 重出：`python scripts/qa/rerender-previews.py --data <desktop-runtime/data> --sample <带 EXIF 的样片>`。
- 当前山景样片是放大件（源 1226×920 → 2667×2000）。**只够预览用**；
  若要把它当编辑器示例照片，会糊，需要真原图。

### 4.3 导出尺寸链

`inspector/OutputSize.kt`（Family/Aspect → canvas）→ 桌面 `ExportEstimate.canvasOf`
（引擎 `fit.source_canvas` → Shell 公式 → 测量）→ 导出命名
`ExportNaming.exportPath(..., capturedAt)`。改任何一环都要同时看：
预览裁切提示、像素估算、导出实际尺寸、文件名里的日期。

### 4.4 自动字标（logo）

两端都在 Kotlin 里解析：`PhotoBrandKeys.brandKeyFor(photoMake)` +
`LogoBrandCatalog.autoCutForBrandKey`，然后把**具体字标**塞进 design JSON。
用 `e4hand` 命令行验证时没有 `--design` 参数，必须临时改 `hand/cards.json` 指向一个
带 `design.logo{name,width,height,dataUrl}` 的 design 文件——否则会画卡自带字标
（比如 Panasonic），看起来像「双端不一致」，其实是测试口径不同。

### 4.5 架构闸门

- `EvidenceHookKonsistTest`：shell/产品层不能出现 `FM_*` 字面量，日志标签别用 `FM_` 前缀
  （用 `PICKER_UNAVAILABLE` 这种）。
- `ArchAllowlistHygieneKonsistTest`：allowlist 不能有陈旧条目。

## 5. 发布流程（照做即可）

1. 改 `version.properties`（versionName / versionCode 各 +1），提交。
2. `fm_build_rc.cmd --package`，确认 `build-report.json` 的 `result: PASS`。
3. 打 MSI（见第 2 节），记下 APK/MSI 的 **size 与 sha256**。
4. 改 `updates/latest.json`：versionName/versionCode/notes/两个资产的 url+sha256+size/releasePage。
5. `git push origin ui-v2/main`，取回头提交的 **完整 SHA**。
6. `gh release create v0.9.0-rcNN --prerelease --target <完整SHA> --title ... --notes ... <apk> <msi>`。
   **`--target` 必须给完整 SHA 或分支名**，短 SHA 会 422 `target_commitish is invalid`。
7. 校验：`gh release view ... --json assets` 两个资产 `uploaded`；两个下载链接 200；
   `raw.githubusercontent.com/.../ui-v2/main/updates/latest.json` 是新的版本号。

## 8. rc57 之后：玻璃三张卡的画幅（2026-11-23）

rc57 把 `glassSideCard` 的两张卡改成「跟照片比例走」（`cardFit=photo` + `canvasAspect=0`），
但画布仍然跟照片一样大：4:3 横图时卡片顶满可用宽度，照片从画布 **13.18%** 处就开始
（冻结构图是 45.93%），F/MM/S 三个数值压到照片上，上下留白从 5.65% 涨到 13.18%。
本轮把画布**由构图推出来**，既保住构图又不裁照片。**动这三张卡之前先读这一节。**

### 8.1 玻璃 05：画布 = 构图（照片不裁，比例跟着照片走）

数据保持 rc57 的 `canvasAspect=0` + `cardFit=photo`（`designs/glass-pill-5.json` 的
`design.params` / `variant.params` 两块）。画布不再写死 1.4971，改由
`glass_side_card.rs` 的 `layout()` 推：

```
画布宽高比 = 卡片宽高比 × (cardHeightPct/100) ÷ ((1 - 2·cardInsetPct/100) × cardMaxWidthPct/100)
           = 卡片宽高比 × 0.887 / 0.4089 = 2.1692 × 照片宽高比      （默认参数）
```

于是任何照片比例都保住冻结构图：照片从 **45.93%** 开始、卡片 **40.89%W / 88.7%H**、
上下留白 **5.65%**，照片完整入卡。4:3 输入 → 画布 2.89:1、3:4 → 1.63:1、1:1 → 2.17:1、
16:9 → 3.85:1。`cardMaxWidthPct` 缺省 **55.53**（参考设计 419/(1024−2×135)）同时是
画布推导系数和「卡片最多占可用宽度」的上限，两边同一个数，正常构图不会被收口。

**别再**把画布写死回 `canvasAspect=1.4971`（3:4 输入也会输出横图，等于裁照片），
也别删 `cardFit`（卡片会被固定 0.69 窗口裁）。改 `cardHeightPct` / `cardInsetPct` /
`cardMaxWidthPct` 会同时改画布宽高比，改完用 8.3 的方法复核。

### 8.2 玻璃色卡 / 液态玻璃（按观感修，不照原版）

- `glass_palette_portrait.rs`：面板宽度**不再随高度封顶收缩**。高度由
  `panelWidthPct` / `panelHeightPct` 换算出的面板自身比例（676:310）决定，只在极宽画布上
  按 `panelMaxHeightPct`（缺省 60）封顶；封顶后网格等比缩小，六个色值始终在面板里。
  旧版 4:3 上面板从 89.2% 缩到 54%，通栏色卡变成居中一小块。
- `glass.rs` 胶囊：高度只由宽度推出（`pill_aspect` 7.1619 stack / 8.6914 单行），
  字号按胶囊高度换算。旧版按短边 `s` 取高又按 `s` 取字号，竖图时胶囊被撑成 4:1、
  字缩到短边尺度上（「框显厚、字变小」）。
- `glass_side_card.rs` 文字块装不进面板时（`panel_avail * 0.96`）整组等比缩小——
  顺带修掉「玻璃卡片 3:4」把 `1/400` 压到照片上。

注意：这两张卡现在**故意偏离原版 Electron**。原版玻璃色卡的画布恒定 3:4（横图会被裁），
液态玻璃在 3:4 输入下是 4:1 的厚胶囊（原版实测见
`evidence/glass-aspect-20261123/options/original-app-4-aspects.png`）。玻璃 05 的原版也是
写死 1.4971 画布；本轮选的是「构图不变、画布随照片」的 C 方案，四种语义的对照图在
`evidence/glass-aspect-20261123/options/glass05-four-semantics.png`。
